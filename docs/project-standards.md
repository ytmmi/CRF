## 1. 规范用语与优先级

### 1.1 规范用语

- **必须**：不满足即禁止构建、合并或发布。
- **禁止**：不得实施；如确需例外，必须先修改本文并记录理由。
- **应该**：默认执行；偏离时必须在构建记录中说明原因和补偿验证。
- **可以**：在不违反更高等级规则时自由选择。

### 1.2 文档冲突处理

发生冲突时按以下顺序处理：

1. 本项目标准中的安全、正确性、可维护性和构建门禁；
2. 根目录 `crf格式标准.md` 对**已经发布码流**的字段与解码语义；
3. 当前已批准的专项规划；
4. API、架构、开发和用户文档；
5. 优化评审中的历史记录。

历史文档不能覆盖最新明确决策。发现冲突时，实施者必须先标出“现状、目标、迁移方式”，
不得自行混合两套语义。

## 2. 不可妥协的项目原则

| 标准 | 强制要求 |
|---|---|
| 管线边界 | 有损与无损是两条并行管线；不得用有损优化改变无损语义 |
| 无损正确性 | 无损输入与最终输出必须逐像素、逐分量一致 |
| 有损正确性 | 只能使用文件内可获得的重建参考；文件必须自包含解码 |
| 压缩目标 | 在质量底线内持续降低码率；达到 AVIF 只是一阶段目标，不是停止点 |
| 首帧优先 | 首帧是当前有损压缩第一优先级，但不得把误差或字节转嫁给后续帧 |
| 单文件规模 | 所有手写源文件必须不超过 1000 个物理行；800 行起进入拆分预警 |
| 单一职责 | 一个模块只承担一个主要职责；禁止把多项不相干功能杂交在同一文件或类型中 |
| 构建门禁 | 每次构建前必须完成可维护性、文件行数、依赖方向和测试影响检查 |
| 格式兼容 | 编码端和解码端必须对称；任何码流变更必须版本化并验证旧文件 |
| 批量/流式 | 在相同 resolved config 下，批量和 streaming 的语义必须一致 |
| 参数透明 | 禁止静默忽略、截断或回退用户参数；必须返回错误或可查询告警 |
| 数据驱动 | 新算法必须有基线、消融、收益和停止门槛，不凭直觉长期堆积工具 |
| 版本命名 | 项目版本号遵循 `a.b.c.d` 规则（见 §13）；每次 git push 前必须递增，禁止同一版本号重复推送 |

## 3. 文件规模与功能拆分

### 3.1 1000 行硬限制

所有项目手写代码均采用格式化后的**物理行数**计数，包括注释和空行：

- Rust：`.rs`；
- 前端：`.ts`、`.tsx`、`.js`、`.jsx`、`.css`；
- 项目维护的构建、测试和迁移脚本；
- 其他包含业务或算法逻辑的手写源文件。

规则如下：

- `0..799` 行：正常；
- `800..1000` 行：预警。除拆分、修复和清理外，不得继续加入大块新功能；
- `>1000` 行：硬失败，禁止构建、合并和发布，必须先完成职责拆分。

生成代码、第三方 vendor、构建产物和锁文件不计入，但必须能由工具明确识别，且禁止
手工把业务逻辑塞进这些文件以规避限制。测试文件同样受 1000 行限制。

后续首次进入代码实现时，必须增加统一源码规模检查脚本（建议放在 `scripts/`），并让
本地标准构建入口和 CI 在编译前调用。脚本至少输出超限文件、行数和退出失败码；在脚本
落地前，每次构建必须执行等价的人工/命令检查并记录结果。禁止只在发布前检查。

### 3.2 必须按功能拆分

超过限制时必须按稳定职责拆分，例如：

```text
encoder/
  sequence.rs        # 序列编排与阶段顺序
  first_frame.rs     # 首帧编码和本地重建
  reference.rs       # 重建参考选择与残差生成
  rate_control.rs    # 质量/码率控制
  frame.rs           # 单帧公共入口

tests/
  lossless.rs        # 无损往返与兼容
  lossy.rs           # 有损量化与质量
  reference.rs       # golden/previous 闭环
  streaming.rs       # 批量/流式一致性
```

禁止使用以下伪拆分：

- `part1.rs`、`part2.rs`、`misc.rs`、`helpers2.rs` 等按文件长度切块；
- 两个文件互相访问大量私有状态，只是把同一巨型函数机械分段；
- 把编码、解码、测试、日志和基准代码混在一个模块；
- 把所有共享逻辑堆入无边界的 `utils` 或 `common`；
- 让 `mod.rs`、`main.rs` 或 Tauri command 成为业务逻辑汇集点。

### 3.3 单一职责判定

一个文件必须能用一句话描述其主要职责。出现以下任一情况即必须评估拆分：

- 同时处理两种以上独立生命周期，例如“解析参数 + 编码算法 + 写文件”；
- 同时属于两个架构层，例如“Tauri IPC + CRF 变换实现”；
- 修改一个算法时被迫触碰不相关 UI、导出或测试工具逻辑；
- 私有函数分成明显互不依赖的功能簇；
- 文件需要多个“区域”标题才能解释其存在原因；
- 新功能只能通过继续增加模式分支、布尔组合或特殊质量编号分支接入。

函数超过约 120 行、嵌套超过 4 层或参数持续增加时应拆成具名阶段；这属于审查预警，
不能用拆成大量无语义小函数替代真正的模块边界。

### 3.4 当前预警文件

截至 2026-08-26 的源码规模检查：

- `src-tauri/src/test/mod.rs`：约 **1030 行，已超过 1000 行硬限制**；
- `src-tauri/src/crf/encoder/tests.rs`：约 **980 行，处于拆分预警区**；
- `src-tauri/src/crf/format/prediction.rs`：约 **801 行，处于拆分预警区**。

因此当前源码状态不满足本标准的构建准入：后续任何实质功能构建前，必须先按测试领域
和预测职责拆分上述文件，并重新执行规模检查。不得继续向这些文件集中追加性能、算法
或测试功能。构建产物中第三方生成的超长文件不属于手写源码检查范围。

## 4. 架构边界

### 4.1 分层职责

| 层/模块 | 允许职责 | 禁止职责 |
|---|---|---|
| 前端组件 | 展示、交互、输入校验提示 | 实现编解码算法或解释原始码流位 |
| 前端 service | 类型安全地调用 Tauri | 保存算法状态或复制后端默认参数逻辑 |
| Tauri commands | 参数反序列化、权限边界、错误转换 | 编码循环、变换、量化、熵编码 |
| 参数解析 | 校验、继承、预设解析、resolved config | 图像遍历、熵编码和文件 I/O |
| encoder sequence | 阶段编排、参考生命周期、帧级调度 | 具体 DCT、CABAC、指标计算、UI 日志格式 |
| frame/intra | 单帧候选组织与 RDO | 文件级索引、Tauri、图像导出 |
| transform | 可逆/有损变换及其数学测试 | 码流组装、参数 UI、磁盘访问 |
| entropy | 符号化与位流读写 | 质量预设、图像预处理、参考选择 |
| decoder | 严格按码流重建与边界校验 | 猜测编码器配置或读取源图补偿 |
| metrics/benchmark | PSNR/SSIM、字节、速度报告 | 进入生产码流或改变编码决策，除非明确作为 RDO 模块 |
| tests | 断言和测试夹具 | 生产路径所依赖的唯一实现 |

### 4.2 依赖方向

推荐依赖方向为：

```text
UI → Tauri command → public codec API
                         ↓
                 config / sequence
                  ↓      ↓      ↓
              frame   transform entropy
                         ↓
                      format
```

- 底层 `format/transform/entropy` 禁止反向依赖 Tauri、UI 或测试。
- 编码器与解码器可以共享纯格式定义和纯数学原语，禁止互相调用高层入口形成环。
- 批量与 streaming 必须复用公共首帧、参考、参数和单帧逻辑，不得复制一套近似实现。
- `unsafe`、SIMD 和平台分派必须隔离在小型模块，并提供标量参考实现对拍。

### 4.3 禁止多功能杂交

禁止为了减少文件数量而把多种功能合并。典型禁止案例：

- 在 `sequence.rs` 同时实现首帧 intra、运动搜索、质量指标和码流写入；
- 在 `quant.rs` 解析 CLI/JSON、选择预设并执行像素量化；
- 在 `decoder/mod.rs` 同时导出 PNG、修复损坏文件和实现各 frame type；
- 在测试运行器中重新实现生产解码恢复逻辑；
- 为多个算法增加一个统一“万能上下文”结构，导致所有模块都能修改所有状态；
- 一次提交同时混合无关的格式变更、算法新增、UI 改版和性能重构。

一个完整功能可以跨多个模块，但每个模块仍须保持单一职责；“同一需求”不等于“必须
放进同一文件”。

## 5. 无损与有损管线标准

### 5.1 管线隔离

- `None`/无损选择必须走无损管线；有损参数不得被读取或产生副作用。
- 无损输出必须逐像素、逐分量等于输入；可逆变换必须有数学往返测试。
- 有损优化不得通过共享默认值、全局开关或格式标志改变无损产物。
- 公共工具只有在语义完全相同并有两条管线回归时才能复用。
- 每次修改有损路径都必须运行无损回归；反之亦然。

### 5.2 有损目标预设

- 目标高质量预设记为 `Q_target`，其公开编号必须由率失真标定决定，可为 Q95、Q96、
  Q97 或其他值。
- 不能为保留编号而扭曲目标质量，也不能只给较低质量结果提高编号。
- 较高编号必须统计上具有不低于较低编号的质量；总体积通常也应单调。
- Q75/Q90/Q95/Q96/Q97 必须联合标定，不允许把 `quality == 95` 等特殊算法分支继续
  散布到管线各处；预设应解析为版本化配置。
- 标准预设之外必须支持精细参数覆盖和完全显式配置；显式配置不得冒充标准预设。

### 5.3 有损首帧与重建参考

首帧有损时必须先编码并在编码端本地解码得到 `G_hat`，后续帧只能基于 `G_hat` 生成
残差：

```text
G_hat       = decode(encode(frame0))
residual[i] = original[i] - G_hat
restored[i] = G_hat + decoded_residual[i]
```

禁止：

- 后续残差基于原始 frame0，而文件解码使用有损 frame0；
- 测试或查看器重新加载源 frame0 参与文件恢复；
- 用隐藏外部文件、缓存或编码器状态补全解码；
- 通过降低后续帧质量掩盖首帧字节收益。

后续探索 previous/hybrid 参考时同样只能引用已重建帧。首帧先完成会形成一个阶段依赖，
但其余 golden 残差帧仍应保持可并行和可随机访问的设计目标。

### 5.4 率失真决策

- 无损候选在解码结果相同时可以按完整字节数取最小，保证单调不劣化。
- 有损候选质量不同，必须按 `J = D + λR` 或带硬质量约束的码率最小化选择，禁止只按
  最小字节选择。
- 失真必须基于实际解码重建；预测只能引用已重建邻域。
- PSNR/SSIM 是可复现护栏，不替代正常观看、关键区域放大和最差帧检查。
- 新工具必须提供逐项消融；收益低于专项规划停止门槛时不得进入正式格式。

### 5.5 AVIF 对标合同

当前正常尺寸主对标固定为 `E:\multimedia-compress\avif.py` 的：

```text
av1_nvenc / preset p7 / vbr / cq=18 / yuv420p
bt709 colorspace + primaries + transfer / full range
```

- 必须使用相同输入预处理、尺寸、色彩和 alpha 语义。
- 必须比较完整文件字节、frame0 字节、全局与逐帧质量、最差帧。
- 现有受源 golden 恢复影响的质量结果只作诊断，P0 闭环修复后必须重测。
- 达到 AVIF 同质量体积只是阶段 B；仍应在视觉质量底线内继续压缩。
- 无损 AVIF/HEVC 数据属于无损旁证，禁止混入有损主榜。

### 5.6 当前算法优先级

后续实现顺序必须遵循：

1. 文件自包含解码和 reconstructed-golden 正确性；
2. 目标质量预设、4:2:0 和亮/色度精细量化；
3. 首帧“局部预测 → 残差变换 → 量化/RDOQ → 系数熵编码”；
4. 逐块 EOB、扫描、significance、DC/AC 上下文；
5. 感知保护和扩展数据集标定；
6. 重建参考竞争、稀疏变化、轻量位移、场景切换和序列码率控制；
7. 码率方案稳定后再做速度优化。

未经项目标准变更，不引入需要训练或运行模型的 ML 编解码依赖，不直接复制完整 AV1
复杂度，也不以内嵌外部 AVIF 码流代替 CRF 算法建设。

## 6. 参数与公开接口标准

- 预设必须只是版本化默认配置，解析后与自定义配置走同一路径。
- `None`（继承）、`Auto`（内容自适应）、`Enabled/Disabled`（强制开关）必须可区分。
- 核心配置使用有明确单位的定点整数；JSON/UI 小数必须按规定精度转换。
- 参数必须注明类型、单位、范围、默认、作用域、互斥关系、格式影响和失败行为。
- 禁止静默忽略未知字段、溢出、截断、自动降级或同时接受相互冲突的新旧配置。
- 必须提供编码前 `validate/resolve` 能力和 resolved config；批量/streaming 共用同一结果。
- API version、preset revision、bitstream version 必须分开管理。
- 稳定参数和实验工具参数必须分层；实验参数需要显式 opt-in。
- 完整规范以 `lossy-tuning-interface-plan.md` 为实施依据。

## 7. 码流格式与兼容标准

### 7.1 格式变更前置要求

任何新增 frame type、flag、字段或载荷语法必须先形成文档，至少包含：

- 字节/位布局、大小端、取值范围和保留值；
- 编码条件、解码步骤和边界行为；
- 版本或 feature bit；
- 旧文件解码、新文件拒绝/兼容策略；
- 批量、streaming、内存解码和文件解码的对称设计；
- 损坏、截断、越界和未知值的错误行为；
- 实际信令成本后的净收益。

没有真实数据收益或低于既定门槛的新语法不得占用格式位。

### 7.2 解码安全

- 所有长度、偏移、维度、帧数、乘法和内存分配必须先做溢出与边界检查。
- 未知关键版本、非法组合和不支持工具必须返回结构化错误，禁止猜测。
- 保留位按规范校验；不能把“当前恰好为零”的位视为可随意复用。
- CRC/校验失败不得输出伪装成成功的完整结果。
- 解码器不得依赖源图、编码参数默认值或外部 codec 才能还原 CRF 文件。

### 7.3 编解码对称

格式变更必须在同一功能范围内同时设计 encoder、decoder、streaming、索引和测试。
允许分阶段提交探针，但探针不得写入正式码流。禁止先输出一种新语法，再依赖后续提交
补解码器或边界校验。

## 8. 测试与基准标准

### 8.1 每类变更的最低验证

| 变更 | 必须验证 |
|---|---|
| 纯重构 | 格式化、静态检查、原有测试、关键产物逐字节一致 |
| 无损算法 | 单元测试、随机/边界往返、逐像素一致、候选单调性、旧文件解码 |
| 有损算法 | 文件自包含恢复、逐帧质量、最差帧、frame0/总字节、消融、无损回归 |
| 格式变更 | 新旧版本、非法/截断输入、encoder/decoder 对称、批量/streaming |
| 参数/API | 范围、默认、继承、冲突、序列化往返、未知字段、resolved config |
| 性能优化 | 优化前后输出一致；基准需说明数据、轮数、冷/热状态和方差 |
| UI/Tauri | 类型契约、错误传播、取消/进度、后端参数有效值展示 |

### 8.2 必须保留的回归性质

- 无损逐像素一致；
- 文件 CRC 和索引正确；
- 批量与 streaming 在相同配置下语义一致；要求逐字节一致的路径必须锁定字节；
- deterministic 模式相同输入、版本和 resolved config 产生相同码流；
- 有损恢复只使用 decoded references；
- 较高质量编号不得在分层验证集上系统性低于较低编号；
- 旧格式样本持续可解码；
- SIMD 与标量参考实现逐值对拍；
- 错误输入不会 panic、越界分配或静默成功。

### 8.3 数据集与报告

- 固定保留 1/1000/2/2000/3/5/c 回归组。
- 有损算法扩展集至少包含 30 个互不重复的序列首帧，并按线稿、赛璐璐、渐变、照片、
  JPEG/WebP 源、UI/像素画、高饱和边缘、透明/CMYK 和尺寸分层。
- 同一序列的相邻帧不能冒充独立样本扩大胜率。
- 必报完整字节、bpp、frame0 字节/占比、全局及逐帧 PSNR/SSIM、最差帧、速度、内存、
  工具胜出率和消融。
- 对标输入预处理不一致时，样本不得进入主榜。

## 9. 每次构建的强制流程

这里的“构建”包括 `cargo build/check/test`、`cargo clippy`、NVIDIA feature 构建，以及为验证
算法而生成新 CRF 产物的实现轮次。项目为**纯 CLI**，无前端构建（pnpm/Tauri 构建不存在）。

### 9.1 构建前门禁

每次构建前必须回答并记录：

1. 本轮唯一主要目标是什么？是否混入无关功能？
2. 修改属于哪一层、哪个模块？依赖方向是否正确？
3. 是否让一个文件或类型承担新的第二职责？
4. 所有手写源文件是否 `<=1000` 行？是否有文件进入 `>=800` 行预警？
5. 若进入预警，是否先完成按职责拆分，而不是继续堆叠？
6. 是否改变无损、有损、参考、参数或格式语义？对应测试和文档在哪里？
7. 是否存在可复用的公共原语？复用会不会把两条管线错误耦合？
8. 是否引入依赖、格式位或公开 API？是否有更小的边界方案？
9. 是否保留用户已有修改，避免顺手重写无关代码？

任一硬门禁未满足时，禁止开始构建；先重构、补文档或缩小变更范围。

### 9.2 推荐执行顺序

在实际命令可用时，按风险从低到高执行：

```text
源码规模检查
→ 格式化检查
→ 静态检查 / lint
→ 受影响模块单元测试
→ 编解码往返与兼容测试
→ 批量/streaming 一致性测试
→ 完整测试
→ release build
→ 质量/压缩率/速度基准
```

不得为了得到构建成功而删除、放宽或跳过失败测试。若环境无法执行某项，必须在交付中
明确说明“未验证”，不能写成通过。

### 9.3 构建后审查

构建成功不代表可交付。构建后必须再次检查：

- 是否生成未预期文件、临时数据或被错误纳入版本控制的产物；
- 是否出现文件超过 1000 行或模块职责扩散；
- warning 是否为零；错误是否被转换成静默 fallback；
- 产物是否符合对应的正确性、质量、体积和兼容门槛；
- 文档、默认值、API 示例是否与真实代码一致；
- 是否可以删除重复代码、调试开关和一次性探针。

### 9.4 构建记录模板

每个实现轮至少记录：

```text
目标：
修改模块及职责：
格式/API 影响：无 / 有（版本与迁移）
最大手写源文件：路径 + 行数
800 行以上文件及拆分处理：
执行的检查与测试：
未执行项及原因：
无损结果：
有损质量/字节结果：
批量/streaming 结果：
兼容结果：
新增依赖：
已知风险与停止/回退条件：
```

## 10. 代码质量与错误处理

- Rust 遵循 `rustfmt`；`clippy` warning 必须处理，不用全局 allow 掩盖。
- TypeScript/React 遵循 ESLint 和 Prettier；禁止无理由使用 `any`。
- 生产代码使用结构化错误；禁止对输入、I/O 和解码数据使用无保护 `unwrap/expect`。
- 编码热路径的 panic 必须只代表内部不变量，并有测试证明；外部输入错误必须返回结果。
- 魔数、质量阈值、格式位和矩阵必须具名、集中并有单位说明。
- 布尔参数超过两个且存在组合语义时，优先改为枚举/结构体，避免非法状态。
- 公共 API 只暴露必要面；内部工具保持 `pub(crate)` 或更窄。
- 注释解释“为什么、约束和不变量”，不重复逐行代码。
- 禁止复制一份生产逻辑到测试或 streaming 后单独维护。

## 11. 性能、并行与依赖

- 正确性、码率方案和模块边界优先于微优化。
- 性能修改必须有 profile 或基准依据；不得凭估计引入复杂缓存、线程池或 unsafe。
- 并行任务不得共享可变编码状态而产生非确定结果；顺序依赖必须在阶段边界明确表达。
- Fast-Fail 只允许数学上不改变胜者的剪枝；启发式剪枝必须受 effort 控制并对拍全搜索。
- 内存按图像尺寸、帧数和候选数做上界分析；大图不得隐式复制整序列。
- 新依赖必须说明用途、许可证、平台支持、维护状态、二进制体积和是否可由现有代码替代。
- 禁止为了单一小功能引入大型运行时或外部 codec 依赖。

### 11.1 原生动态库与 GPU 分发

涉及原生加速后端时，发布包必须遵循标准的 `exe + dll` 布局：

- Windows NVIDIA 构建必须使用 workspace 构建，同时生成 `crf-viewer.exe` 和
  `crf_cuda.dll`；两个文件必须保持同一架构、同一版本并放在同一发布目录。
- GPU 后端实现、PTX 和厂商 API 适配代码放在 `crf_cuda.dll`，主 EXE 只能通过稳定的
  C ABI/窄加载层调用，禁止把 GPU 后端重新静态链接或嵌入 EXE。
- `crf_cuda.dll` 只允许动态依赖目标机的 NVIDIA 驱动 `nvcuda.dll`；不得要求目标机安装
  CUDA Toolkit、`nvcc` 或 `cudart.dll`。驱动 DLL 属于系统组件，不随应用复制。
- 发布前必须验证 DLL 确实出现在安装包/压缩包中，并在无 NVIDIA 设备、DLL 缺失和驱动
  异常时验证 EXE 可启动且自动回退 CPU。
- CPU-only 构建可以省略 `crf_cuda.dll`，不得因缺少该 DLL 阻止 CPU 模式启动。
- 本地诊断可使用 `CRF_CUDA_DLL` 指定 DLL 绝对路径，但不得把开发机 Toolkit 路径写死
  到生产代码或发布脚本中。

## 12. 文档标准

每个行为变更必须同步更新对应文档：

- 码流字段：根格式标准；
- 公共参数/API：接口文档及示例；
- 架构职责：架构文档；
- 构建/测试命令：开发文档；
- 算法结论、基线和停止决策：专项规划或优化评审；
- 用户可见行为：README/用户指南。

文档必须区分“已实现”“规划”“实验探针”和“历史结果”。禁止把计划写成已交付，也禁止
让旧数字覆盖新口径。所有基准注明日期、数据集、工具版本、参数、字节口径和质量口径。

## 13. 版本号命名规则

项目版本号采用四段式 `a.b.c.d`，当前版本为 **0.3.1.1**，后续版本更新从此版本演绎递增。

| 段 | 含义 | 递增时机 |
| :-- | :-- | :-- |
| `a` | 大型更新 | 里程碑式升级，如开发版 → 测试版 → 正式版 |
| `b` | 兼容性 | 出现不兼容旧版本的更新（如格式/API/行为破坏性变更）时增加 |
| `c` | 常规更新 | 常规功能新增、增强 |
| `d` | bug 修复 | 缺陷修复、微小修正 |

### 13.1 递增规则

- 每次 git push 前必须递增版本号，禁止同一版本号重复推送（硬门禁）。
- 变更属于哪一档，就递增对应段位，并清零其右侧所有段位。例：
  - bug 修复：`0.3.0.0 → 0.3.0.1`
  - 常规更新：`0.3.0.0 → 0.3.1.0`
  - 兼容性变更：`0.3.0.0 → 0.4.0.0`
  - 大型更新：`0.3.0.0 → 1.0.0.0`
- 一次提交包含多类变更时，按最高档位递增一次，不重复累计。
- 纯文档、注释、测试调整也属于变更，须递增（最低 `d` 档）；如与代码变更同行，
  合并按代码变更档位递增一次。

### 13.2 版本号的落地位置

`a.b.c.d` 是项目的唯一正式版本号，同一版本须同时同步到以下位置，禁止一处更新
另一处遗漏：

| 位置 | 写法 | 说明 |
| :-- | :-- | :-- |
| 本文档 §13 | `0.3.1.1` | 唯一权威来源 |
| `Cargo.toml`（`crf-viewer` 与 `crf-cuda`） | `0.3.1`（省略 `d`） | Cargo 仅支持三位 semver；`a.b.c` 三段必须与正式版一致 |
| CLI（`crf-viewer --version`） | `0.3.1.1` | `src/main.rs` 常量 `APP_VERSION` 输出完整四位 |
| git tag / 发布命名 | `v0.3.1.1` | 发布时打完整四位 tag |

- `Cargo.toml` 的 patch 位与 `d` 段独立：Cargo 内的 `0.3.1` 不代表 `d=0` 已固化，
  纯 bug 修复推送时只递增 `d`，`Cargo.toml` 三段保持 `0.3.1` 不动。
- 推送前检查：确认 §13 表格、`Cargo.toml`、`APP_VERSION` 常量三处版本一致且高于上一次推送，
  再执行 push。

## 14. 变更组织与审查

- 一轮实现只设一个主要目标；必要的对称 encoder/decoder/test/docs 属于同一目标。
- 大功能按“接口/探针 → 正确性 → 正式语法 → 优化 → UI”分阶段，阶段间可独立验证。
- 纯重构与算法行为变更应该分开；若无法分开，必须先建立字节/像素基线。
- 不得顺手修复与任务无关的文件，避免扩大回归面。
- 新模块名必须反映领域职责，禁止使用含糊命名掩盖杂交设计。
- 审查必须关注可删除性：实验失败时能否移除而不破坏其他功能。

## 15. 完成定义

一项构建任务只有同时满足以下条件才算完成：

- 需求和成功门槛已实现；
- 所有手写源文件不超过 1000 行，800 行以上文件已有拆分处理或未继续增长；
- 模块单一职责明确，没有新增多功能杂交文件；
- 格式/API/参数变化完成版本、迁移和边界设计；
- encoder/decoder、批量/streaming、无损/有损的受影响路径均已验证；
- 测试、静态检查和构建结果真实记录，未执行项明确披露；
- 算法变更有基线、消融、质量/字节/速度结果和回退条件；
- 文档与代码一致，无临时探针、调试产物或重复实现残留；
- 用户已有修改未被覆盖，无关文件未被重写。

## 16. 标准变更

本文是强制标准，但不是不可演进。修改标准必须：

1. 明确现有规则阻碍了什么真实需求；
2. 给出替代约束和风险控制，而不是简单删除门禁；
3. 同步评估格式、兼容、测试和维护成本；
4. 在优化评审中记录决策日期和影响范围；
5. 在标准变更生效前，不得先用代码事实倒逼文档追认。

尤其是“单文件不超过 1000 行”和“禁止多功能杂交”两项属于长期硬标准，不得以赶进度、
一次性实验、模型上下文不足或构建能够通过为理由豁免。
